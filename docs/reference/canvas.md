# Canvas API

The drawing surface. 480×320, 4 bits per pixel, indexed against a sixteen
colour palette, with dirty-rectangle output.

Header: `gui/canvas.h`. The reasoning behind the format is in
[why 4 bpp](../explanation/why-4bpp.md) — read that before proposing a change
to it, because the alternatives were costed and rejected rather than
overlooked.

## Palette

Slots 2, 3 and 4 are the CaDS mark's own colours, so the device and the
documentation look like one product.

| Slot | Name | Colour |
|---|---|---|
| 0 | `CadsColorBlack` | `#000000` |
| 1 | `CadsColorWhite` | `#FFFFFF` |
| 2 | `CadsColorBrand` | `#204C86` |
| 3 | `CadsColorBrandLight` | `#B5C4D8` |
| 4 | `CadsColorAccent` | `#9CB33B` |
| 5–7 | `CadsColorGrayDark/Gray/GrayLight` | |
| 8–10 | `CadsColorRed/Amber/Teal` | |
| 11 | `CadsColorBrandDark` | `#12305A` |
| 12 | `CadsColorSurface` | `#F2F5F9` |
| 13 | `CadsColorMagenta` | |
| 14 | `CadsColorLionMid` | |
| 15 | `CadsColorBackground` | `#101418` |

`cads_canvas_set_palette()` re-tints everything drawn in that slot at the next
flush, which is what makes a theme one table rather than a repaint.

The palette is stored **pre-byte-swapped** to big-endian RGB565: the panel
wants the high byte first and the SPI DMA emits bytes in memory order, so
holding the swap here turns per-pixel conversion into a lookup and a store.

## Drawing

```c
cads_canvas_clear(CadsColorBackground);
cads_canvas_fill_rect(0, 0, CADS_CANVAS_WIDTH, 40, CadsColorBrand);
cads_canvas_draw_text(12, 8, &cads_font16, "CaDS Zero", CadsColorWhite);

cads_rect_t box = {0, 100, CADS_CANVAS_WIDTH, 30};
cads_canvas_draw_text_aligned(box, CadsAlignCenter, &cads_font24, "Leo", CadsColorBrandLight);

cads_canvas_flush();   /* pushes only what changed */
```

`cads_canvas_draw_text()` places the **top of the line box** at `y`, not the
baseline, and returns the pen position so runs in different colours chain.
Laying out a strip is far more often "at the top of that band" than "on a
baseline".

## Clipping

```c
cads_rect_t area = {100, 100, 50, 50};
cads_canvas_push_clip(area);
cads_canvas_fill_rect(0, 0, 480, 320, CadsColorRed);  /* only 50x50 lands */
cads_canvas_pop_clip();
```

Nested clips intersect. Eight levels deep, which is more than any widget tree
here needs.

## Damage and flush

Every drawing call extends one bounding box. `cads_canvas_flush()` converts
that region to RGB565 in 16-row bands, alternating between two staging buffers
so the next band converts while the current one is going out over DMA, and
returns the pixel count actually transferred.

```c
if(cads_canvas_is_dirty()) {
    uint32_t pixels = cads_canvas_flush();
}
```

**A single bounding box is a deliberate simplification.** Two small updates in
opposite corners produce a box covering the screen. A damage *list* would
handle that better and is not implemented, because the widget layouts here do
not generate that pattern and a list costs complexity on the hot path. If a
future app does generate it, measure before building one.

## Images

```c
cads_canvas_draw_image(x, y, &cads_leo);
```

4 bpp indexed, high nibble first, rows padded to whole bytes, with one palette
index treated as transparent. Generated by `scripts/gen_asset.py`.

## Limits

- No alpha, no blending. An indexed buffer cannot express partial coverage
  without spending palette slots on ramps.
- No rotation or scaling.
- Text is 1 bpp and therefore not antialiased, for the same reason.
- Not thread safe. The display is owned by one task and guarded by a mutex;
  see `apps/bringup/tasks.c`.
