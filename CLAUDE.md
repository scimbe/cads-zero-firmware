# CaDS Zero — instance onboarding

Read this first, every fresh start. It exists so a context reset doesn't mean starting over. Keep it current — see the last section.

## What this is

CaDS Zero: clean-room firmware for the ITSboard (STM32F429ZI, NUCLEO-F429ZI + ITS adapter + Waveshare 4" shield). Prefix `cads_`, mascot Leo the Lion, CaDS branding. Explicit clean-room requirement: no lifting code from the vendor's ITS-BRD reference firmware, only its documented pin/behavior facts.

Everything above the HAL layer must build and run for **both** the real board (`targets/itsboard`) and the host simulator (`targets/sim`). If a feature only works on one, it isn't done.

## Non-negotiable safety (docs/SAFETY.md)

Binding, not advisory. Read the actual file, but as a summary: PA13/PA14 (SWD) and PH0/PH1 (HSE) are never repurposed; PF0-7/PG0-5 need care (see the file for which are safe); no mass-erase, ever; flash writes only in `0x08000000`–`0x080FFFFF` (firmware) via the external `st-flash` tool — the `0x08120000` figure elsewhere in that file is the *on-device* flash driver's filesystem-region floor, not a constraint on how you program the chip from outside.

## Toolchain and how to actually debug this thing

- **Build**: `cmake --build build/itsboard` (board) and `cmake --build build/host` (host/sim). Always both, always before flashing. `cd build/host && ctest` for the unit/golden-image suite.
- **RAM budget**: `python3 scripts/check_ram_budget.py` after every board build. There is no heap; this is the whole safety margin. As of this writing the margin is razor-thin (256B against a 256B floor) — a further RAM-hungry change needs an offsetting cut, not just a hopeful build.
- **Flash**: `st-flash --serial <id> write build/itsboard/cads-zero.bin 0x08000000`. Get the ST-Link serial via `st-info --probe`.
- **Serial console**: `scripts/board_cmd.py <letter> [arg] --timeout <n>` for one-shot commands (the explorer's own `?` lists all of them), or use `scripts/cads_serial.py`'s `open_console`/`read_lines` directly for anything needing tighter timing (e.g. opening the port *before* triggering a reset, so you don't race the reboot). Known gotcha: `stty -f` on a `cu.*` device resets the line discipline on close — baud must be set via termios on the same fd you read from, which `cads_serial.py` already does; don't shell out to `stty` separately.
- **st-util + GDB** (`arm-none-eabi-gdb`, resolved from `/Users/dev/.vcpkg/artifacts/.../compilers.arm.arm.none.eabi.gcc/13.3.1/bin/`, not on PATH by default): use `st-util --no-reset` when you want to inspect a hung/crashed board *as it actually is* — plain `st-util` resets on connect, which destroys exactly the state you're trying to read. This is how the SPI mutex bug (2026-08-26) was actually found: attached live, read `bt`/`info registers`/raw peripheral registers, and had the exact faulting line and register state instead of a guess.
- **Crash forensics**: the `E` explorer command dumps `cads_hal_reset_cause()` plus the CCM-resident forensic ring (survives warm reset, holds the last 6 faults with PC/LR/CFSR/HFSR/MSP/PSP and, for a clean `configASSERT`, the exact `file:line`). Check this *before* assuming a boot was clean. Caveat: the ring's binary layout changes when `cads_forensic_record_t` gains fields, so old CCM content briefly reads as one stale, garbled-looking record after such a change — not a new bug, just old bytes misread until it's naturally evicted.
- **Physical/visual verification**: a webcam (ffmpeg, avfoundation on macOS) is how silkscreen labels, physical button positions, and on-panel rendering actually got confirmed this session, more than once, after an assumption turned out wrong. `transpose=2,transpose=2` if the camera is mounted upside down. Don't describe what a physical photo would show — take one.
- **Hard timeouts, always**, on every serial/hardware operation — the Bash tool's own `timeout` parameter (in ms), not a shell `timeout`/`gtimeout` binary (not installed on this Mac). A hung read with no bound has cost real time in this project before.

## Lessons learned (why these rules exist)

- **A third-party debug library's "reset before operating" default can collide with this project's own watchdog handling — check what it actually does to the target, not just what it claims to do.** A WebUSB-based flashing tool (`webstlink`, used for the firmware-lab demo, not this repo's own toolchain) called a `core_reset_halt()` that turned out to be a real `AIRCR.SYSRESETREQ` chip reset, not a debug halt, at the start of every flash operation. That's fine for a chip with no watchdog; on CaDS Zero it re-arms the ~2s IWDG this project deliberately freezes on debug-halt (`DBGMCU_APB1_FZ_DBG_IWDG_STOP`, see the boot-path lesson below) — but only once the core reaches that halted state *again* after the reset, and a WebUSB erase+program sequence's real USB round-trip latency can easily outlast that window, so the watchdog fires mid-operation and resets the chip a second time, out from under the in-progress erase. The tell was `FLASH_CR` reading back as `0x80000000` right after a plain register write — its literal power-on-reset default, i.e. direct evidence of an unwanted reset, not a corrupted read (which is what it looked like for most of the investigation, including one incorrect "isolated to the test harness, not the algorithm" conclusion along the way — that verdict felt decisive, based on a real GDB-vs-Node A/B test, and was still wrong because it never exercised the exact code path that mattered). Fix: only halt the core (`core_halt()`), never reset it, for anything that just needs the CPU stopped rather than the chip rebooted.
- **A working reference on the same hardware is worth more than any amount of theorizing — diff live register state against it.** The Ethernet root cause (2026-08-26: DMABMR.SR reset running *after* MAC config and wiping it, plus PA7 parked on the wrong AF at idle) fell out in minutes once both firmwares were flashed in turn and the full ETH/GPIO register file dumped over SWD (`st-util --no-reset`) at the same execution point. Days of single-sided debugging (counters, Wireshark, PHY registers, timing theories) had circled it without landing. When a known-good implementation exists for the same board, get to a two-column register diff as early as possible.
- **Verify an extracted flash image is `size`-complete (text+data) before trusting any conclusion built on flashing it.** An `objcopy --only-section=ER_IROM1` extraction of an AC6/armlink ELF silently dropped the 184-byte `.data` load copy (armlink emits it as a second `RW_IRAM1` section with VMA=LMA=0x20000000 — no flash LMA to find), producing a vendor binary that booted but had dead networking, which then supported a wrong "the hardware is broken" conclusion for hours. GCC-linked ELFs don't have this trap (`.data` carries a real flash LMA); AC6 ones do.

- **Never assume hardware state from memory.** `st-util`'s reset-on-connect, stale serial buffers, and boards that self-recover via watchdog before you even notice have all produced confidently-wrong conclusions this session. Fresh-check, every time, especially after "it should still be fine" reasoning.
- **A crash that "started" when you added feature X might not be caused by X.** The watchdog-feed tick hook looked like the cause of a new autonomous crash; a dispatched research agent reframed it correctly as an *exposer* of a pre-existing latent bug (the watchdog turned a silent hang into a visible reboot-and-report) — evidence the user had independently supplied without realizing it mattered (a much earlier "I had to press reset, nothing was happening" report). Reframe before you fix; don't let correlation-in-time stand in for causation.
- **When two systems share a resource, look for the missing lock before the missing feature.** The actual root cause of that crash family turned out to be simpler than either the tick-hook or the memory-corruption theories: `cads_hal_spi_claim_bus()`/`release_bus()` was already the checkpoint every caller agreed to use, it just never actually excluded concurrent tasks from each other. Two tasks touching one SPI peripheral with no mutex will eventually race, however rarely.
- **Verify a background agent's diff before trusting it, the same way you'd verify your own.** Check that symbols it references actually exist, that its dependency direction doesn't invert the codebase's own layering, that its claims about library behavior (e.g. what FreeRTOS's static allocation actually fills a stack with) are correct given *this* project's config — then build, test, and flash it yourself. A good agent's confidence isn't a substitute for your own check.
- **Instrument before guessing at a structural fix**, especially under time pressure. Adding precise diagnostics (byte-level touch reads, MSP/PSP in the forensic record, stack canaries, `file:line` on asserts) turned multiple "probably X" guesses into confirmed answers in one hardware cycle instead of several rounds of trial and error.
- **When a config toggle crashes the board, check what code path it actually changes before suspecting the config system itself.** `net.dhcp = 1` crashed the board every time (2026-08-28); reverting the value, rereading the config, and even a from-scratch reformatted filesystem all failed to fix it, and a real power-cycle didn't either — none of that was the cause. The real one: `net.dhcp=1` runs lwIP's DHCP client state machine on the console task's stack, which is visibly deeper than the static-IP path and was already carrying that evening's added call depth (Marauder tick/PCAP/join) — a genuine stack overflow, caught live because `vApplicationIdleHook()` (this project's own stack-guard sentinel) faulted with a garbage PC trying to detect it. Task stacks live in CCM (~59 KB free of 64 KB, separate from the SRAM heap's tight 256 B-floor budget), so the fix (doubling the console stack) was nearly free once found — the hard part was not chasing the toggle's *name* (DHCP) into unrelated systems (filesystem, SWD state) instead of the *code path* it actually exercises.
- **Console silence during a hardware debug session is not proof of a crash — verify with a live GDB attach before trusting it, and double-check which serial port you're actually talking to.** This board enumerates two `/dev/cu.usbmodem*` devices; after one auto-detect hiccup, several "board still crashed" readings during the DHCP investigation above were actually `board_cmd.py` pointed at the wrong (non-console) one. A live `st-util --no-reset` + GDB attach settles it unambiguously either way in seconds — reach for it before extrapolating from a quiet terminal.
- **A prior session's diagnosis of "this needs real porting work" is a hypothesis, not a fact — re-verify by actually running the tool before accepting the harder path.** The ESP32Marauder Bluetooth build (2026-08-28) was assumed to need manual NimBLE 1.x→2.x API porting (~15 compile errors, `HAS_BT` disabled as a workaround) based on an earlier session's diagnosis. Actually running `arduino-cli compile` with `HAS_BT` and the already-present-but-unused `HAS_NIMBLE_2` macro both enabled found, in minutes, that WiFiScan.cpp already ships two complete, correct NimBLE 1.x/2.x implementations gated on exactly that macro — `GENERIC_ESP32`'s own `configs.h` default just left it off while pinning NimBLE-Arduino to 2.3.8, an internally inconsistent default, not an API mismatch. Reading the diff and reasoning about it would not have found this as fast as one real compile did. Same episode also found a real bug in `tools/marauder-build/build_and_flash.sh` itself (a doubled sketch path, present since the script's one commit) purely by running it end-to-end instead of trusting that a script matching an earlier "verified working" claim must itself be correct — the actual verified flash was very likely done by hand, not via that exact script.
- **A fix that isn't hardware-verified isn't done.** Several fixes this session looked correct on read-through and were then proven correct (or, once, proven still-incomplete) only by an actual flash-and-observe cycle. Code review is necessary, not sufficient, for firmware.
- **Dispatch a background research agent for genuinely open technical questions** rather than iterating alone on weak leads — give it the full evidence trail (what's confirmed, what's ruled out and how, exact symptoms), not just the question. This found the touch bug's root cause (a one-transfer SPI read desync) precisely because the prompt included the ruled-out list, not just "why is touch broken."
- **No FreeRTOS API before the scheduler starts — not even object creation.** The boot path flushes the panel (self test + splash, apps/bringup) *before* cads_kernel_start(). Two 2026-08-26 boot crashes both came from the SPI-bus mutex commit doing FreeRTOS work too early: (1) `xSemaphoreTakeRecursive` before the scheduler dereferences a NULL `pxCurrentTCB` → UsageFault INVSTATE, PC=0x0, reset loop with no console output and no forensic record; (2) even just *creating* the mutex (`xSemaphoreCreateRecursiveMutexStatic`) takes a critical section, and before `xPortStartScheduler` runs, `uxCriticalNesting` holds the CM4F port's poison init 0xaaaaaaaa, so the matching exit never restores BASEPRI — it stays clamped at configMAX_SYSCALL_INTERRUPT_PRIORITY (0x50), masking the display DMA's completion IRQ (prio 0x60) so the first boot flush hangs forever (blank white panel). Diagnosis was a live BASEPRI=0x50 read + the FreeRTOS port source + a web check (documented as FreeRTOS-Kernel issue #254). Fixes: gate mutex take/give on `xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED`, and `portENABLE_INTERRUPTS()` right after any pre-scheduler FreeRTOS object creation. When touching the SPI/DMA/display path, remember it runs both pre- and post-scheduler.
- **UPDATED 2026-08-31 - the behavior below has changed; read this note before the rest of the bullet.** As of now, `cads_explorer_app_demo`'s session does the OPPOSITE of what this bullet originally said: it ignores plain ASCII bytes entirely and does NOT exit on one (`board_key.py --help`'s own docstring confirms this deliberately: the reserved key-bytes are all `>= 0x80` specifically so an ordinary typed command "can't accidentally end the session either"). Verified hard, not assumed: repeated `board_cmd.py` calls into a running app-tree session produced zero output and zero effect, confirmed via two live, correctly-detached GDB attaches that the board was healthy and still executing normally both times - only `scripts/board_key.py quit` actually returns control to the console. Original bullet (now historical - true as of 2026-08-28, apparently fixed/changed since) kept below for context:
  Any explorer console byte silently ends the interactive GUI session and stops the panel from updating - this is not a hang, and it will look exactly like one. `apps/bringup/explorer_app_demo.c`'s `d`-command session (what `boot.autostart` uses to drive the panel at boot, `seconds==0` meaning "run until any byte arrives") exits and drops back to the plain console prompt the instant it reads a byte - and nearly every diagnostic (`board_cmd.py`'s `s`/`k`/`i`/`~`/`E`, all of it) is exactly such a byte. 2026-08-28: this produced several genuinely alarming "board frozen, unresponsive" reports mid-session, each one chased with a live GDB attach that (correctly) found a perfectly healthy, idling CPU - because nothing was actually wrong except that the loop calling `cads_gui_tick()` had quietly exited. Before treating "the panel isn't updating" as a hang worth a GDB attach, check whether a console command was sent since the last boot/`d` call - if so, the fix is `board_key.py` (headless key injection, doesn't end the session) or a fresh `d <n>`, not a debugger.
  **Practical upshot either way, old or new behavior**: if a `board_cmd.py` command produces no output at all right after a fresh boot/flash, try `scripts/board_key.py quit` first before suspecting a crash - it's the fix for both versions of this behavior.
- **A UX idea that sounds right on paper still needs a live test before it ships - and reverting a same-day change after honest testing is a good outcome, not a failure.** The Marauder Bluetooth menu items were first built to show/hide based on a `stopscan` liveness probe (no electrical presence line exists on CN8's TX/RX pair, so software liveness was the only signal available) - reasonable given the constraints, but live hardware testing found the 2 s detection window unreliable in practice, with the menu flickering items in and out even with the ESP32 demonstrably connected. Reverted the same session to always-shown (matching the WiFi tools, which never had this problem because they never tried to be clever about it). A working, honestly-reported "this didn't hold up live, here's why, here's the simpler thing that does work" is the correct outcome of trying something real - don't let sunk cost turn a live finding into a shipped bug.
- **A capture device's enumeration index is not stable across separate invocations - look it up by name every single time, never cache it.** The webcam used for visual panel verification (`ffmpeg -f avfoundation`) silently reordered its device index between calls on this Mac, several times producing a photo of the wrong (virtual/placeholder) camera app instead of the one actually pointed at the board - which looked like a camera fault but was purely an indexing assumption. Fix: `ffmpeg -f avfoundation -list_devices true -i "" 2>&1 | grep "<device name>"` fresh immediately before every capture, extract the index from that specific call's output, never reuse a number from an earlier listing.
- **The ST-Link gets "shot down" by three now-confirmed mechanisms (issue #57, 2026-08-27).** (1) macOS auto-mounts the Nucleo's MBED mass-storage drive as `/Volumes/NOD_F429ZI` on every replug and writes metadata to it unasked - the ST-Link interprets writes there as firmware for 0x08000000. This corrupted real flash once: a single cleared bit in the vector table's initial-SP word (0x10010000 -> 0x00010000), board hung in Reset_Handler with wild LEDs, repaired by a plain reflash. `diskutil unmountDisk /dev/diskN` after EVERY replug (find N via `diskutil list external`), or make it permanent with a sudo fstab entry (ask the user): `echo 'LABEL=NOD_F429ZI none msdos rw,noauto' | sudo tee -a /etc/fstab`. (2) Killing an SWD client mid-transfer (a shell timeout SIGKILLing `st-flash write`, a pkill on a backgrounded read) desyncs the ST-Link's protocol state machine - all later commands hit LIBUSB_ERROR_TIMEOUT / chipid 0x000 until a physical USB replug. So: SWD operations get generous Bash-tool timeouts (>=120000 ms for the 896 KB FS region) and are never killed mid-write. This applies to a live GDB *debug* session too, not just `st-flash` (2026-08-28, self-inflicted): a `arm-none-eabi-gdb --batch` session ended with `kill -9` (instead of a clean `continue`/detach) wedged the ST-Link the exact same way. `st-util`'s GDB stub doesn't support GDB's own `detach` command ("Remote doesn't know how to detach") - to actually resume the target and free the ST-Link cleanly, run `continue` as an interactive (non-batch) command and let it send the resume packet before tearing the client down, or just accept a `--connect-under-reset` recovery afterward rather than trusting a hard kill was harmless. (3) All our SWD tooling serializes through `scripts/swd_lock.py` (host-wide flock; `cads_config.py` uses it, shell use: `scripts/swd_lock.py st-flash ...`) so two clients never overlap on the one ST-Link. When a wedge happens anyway: replug, unmount NOD_F429ZI, `st-flash reset`; if the board then boots into wild LEDs, dump 0x08000000 and diff against the .bin before theorizing - it may just need a reflash. (4) 2026-08-29/30, not yet root-caused, hypothesis narrowed: `scripts/cads_config.py push`/`pull` operations were first seen correlating with real, reproducible corruption of the exact same word - `0x10010000 -> 0x00010000` at `0x08000000` - even with NOD_F429ZI never observed mounted (2026-08-29). But 2026-08-30 found the SAME class of flakiness (five consecutive plain `st-flash write` attempts needed before one verified, offsets 43008/30720/0/0/success, no `cads_config.py` anywhere in that sequence) purely from repeated plain firmware writes late in a long session - weakens "it's specifically cads_config.py's read+write pattern" and points instead at general SWD-over-USB reliability degrading with sustained session length/host load, not a specific script. `st-info --probe` and NOD_F429ZI-mount checks were clean between every attempt both times; ST-Link itself never wedged (stayed responsive throughout, just individual write/reset calls needed a retry). Mitigation either way, unchanged: after ANY flash write (not just cads_config.py) verify the board actually boots (console or a photo, not just the tool's own success message) before trusting it, and don't hesitate to retry a failed verify a few times before escalating - it has resolved on retry every single time so far, never needed a physical replug. See docs/ROADMAP.md's 2026-08-29 and 2026-08-30 Log entries for the full evidence trail.

- **`st-flash write` with no following `reset` can leave the core genuinely halted, not running** (2026-08-29, cost real diagnostic time before the pattern was understood: produced its own round of "board unresponsive" false alarms, each one resolved the instant an explicit `st-flash reset` was issued). Always follow a bare `write` with an explicit `st-flash reset` before trusting console/GUI responsiveness - unless immediately chaining into another `write` (`cads_config.py` itself does this internally). A live GDB register read distinguishes "halted, core fine" (PC/SP look sane, nothing changes across samples) from "genuinely crash-looping" (PC parked near `Reset_Handler`/`cads_copy` with a garbage-looking SP that doesn't match the vector table's real initial-SP word) - check before assuming the worse of the two.
  A working, wedge-free live-attach-and-detach recipe (2026-08-29, used to diagnose a real silent boot-loop - see ROADMAP's 2026-08-29 Log entry): `st-util --no-reset` in the background, then non-batch, non-interactive GDB (`-ex` flags, no `--batch`, stdin redirected from `/dev/null`) ending in `-ex "continue"` - GDB blocks there waiting for the target to stop, which it won't on its own with no breakpoints set, so send `kill -INT` (never `-9`) to the *GDB process* once you've read what you needed; GDB catches the interrupt, prints the stop, and - because stdin already hit EOF - exits on its own right after, cleanly. Confirm with `st-info --probe` afterward (should report the one real ST-Link, not "Found 0 stlink programmers" / a libusb exclusive-access warning). Gotcha discovered doing this: backgrounding `python3 scripts/swd_lock.py st-util --no-reset &` and capturing `$!` gets the *Python wrapper's* PID, not `st-util`'s own - the wrapper runs it via `subprocess.run`, a real child process - so killing only `$!` leaves the actual `st-util` binary holding the ST-Link open. Find it with `ps aux | grep st-util` and terminate that PID too (plain `kill`, not `-9` - by the time you're closing this out the SWD bus is idle, not mid-transfer, so a graceful term is safe) before trusting `st-info` again.
  The register signature of "stuck at/near `Reset_Handler`, not a live hang" specifically: PC a few hundred bytes into flash (e.g. `0x0800020c`), every general-purpose register reads `0`, `LR=0xFFFFFFFF` (the CPU's own power-on-reset default, not a real return address or a valid `EXC_RETURN` pattern like `0xFFFFFFF1`/`F9`/`FD`), `SP`/`MSP` still equal to the vector table's initial-SP word, `PSP=0` (never switched off MSP, i.e. the scheduler never got anywhere near running). That combination means the chip is spending nearly all its time back at the reset vector, i.e. a fast reset loop, and console/GUI silence is a real symptom, not the app_demo false alarm - go straight to `st-util --no-reset` rather than re-sending console commands into the void.
- **First real Windows validation pass (2026-09-02, naive-user role, native Windows 11, no WSL): build, flash, and debug all work — this project's own docs undersold Windows before this.** `docs/how-to/vscode-setup.md`'s Windows section previously said "build and debug only, not flash or console"; a full from-scratch install (winget Arm GNU Toolchain — machine-wide only, needs one UAC elevation; stlink-org/stlink's Windows zip for `st-flash`/`st-info`/`st-util`, which needs `libusb-1.0.dll` added by hand — the `libusb` PyPI package bundles a working one — and its chip-config folder copied to a hardcoded `C:\Program Files (x86)\stlink\config`, also elevation-gated) got all the way through build → `st-flash write` → `st-util`+`arm-none-eabi-gdb` stopped at `main()` with a correct backtrace and register read, ST-Link left clean afterward. Found and fixed one real, Windows-only bug along the way: `cmake/arm-none-eabi-gcc.cmake` set `CMAKE_C_COMPILER` etc. to a `CADS_ARM_TOOLCHAIN_BIN`-relative path with no `.exe` suffix — compiler identification still worked (Windows resolves `PATHEXT` for a launched command) but CMake's stricter literal-path check at `project()` failed with "is not a full path to an existing compiler tool" (that check does not apply `PATHEXT`). Never hit on the plain-PATH branch, and never hit on this project's own Mac reference machine — fixed by appending `.exe` only in the `CADS_ARM_TOOLCHAIN_BIN` branch, only under `CMAKE_HOST_WIN32`. Also confirmed the already-documented `st-util` `detach` gotcha applies here too, plus a Windows-specific variant: a non-interactive GDB session with stdin from a closed/empty source loops forever on `quit`'s "Quit anyway?" confirmation instead of erroring - send GDB a plain `kill`, not `detach`+`quit`, in that situation.
